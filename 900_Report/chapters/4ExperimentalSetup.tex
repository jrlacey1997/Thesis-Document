\section{Computational Environment \& Software Stack}
\label{sec:setup_environment}

The experiments were conducted on four workstations running Ubuntu 24.04.5 LTS on an x86\textsubscript{64} architecture. 
The first computer is equipped with an Intel\textsuperscript{\textregistered} Xeon\textsuperscript{\textregistered} CPU E5-1630 v4 @ 3.70\,GHz, providing 4 physical cores and 8 logical processors and 16\,GB of RAM. 
The second computer is equipped with an Intel\textsuperscript{\textregistered} Core\textsuperscript{\texttrademark} Ultra 7 265 CPU, providing 10 physical cores and 20 logical processors and 32\,GB of RAM.
The third computer is equipped with an Intel\textsuperscript{\textregistered} Xeon\textsuperscript{\textregistered} CPU E5-2687W v3 @ 3.10\,GHz, providing 10 physical cores and 20 logical processors, and 16\,GB of RAM.
The fourth computer is equipped with an Intel\textsuperscript{\textregistered} Core\textsuperscript{\texttrademark} i7-8700K CPU @ 3.70\,GHz, providing 6 physical cores and 12 logical processors and 32\,GB of RAM.
As these workstations are materially different in terms of CPU and RAM, the performance results will include notes indicating which workstation was used for each experiment.
Hereafter, the workstations will be referred to as Workstation 1, Workstation 2, Workstation 3, and Workstation 4, corresponding to the order in which they were described above.

The code framework is based on a Python orchestration layer that interacts with a C++ core for computational efficiency. 
\ac{CasADi} constructs the symbolic B-spline dynamics, objective, constraints, and automatic differentiation, while \ac{IPOPT} solves the resulting nonlinear programs with HSL MA27 as the linear solver. 
NumPy provides vectorized numerical operations, including trajectory sampling. 
SciPy provides selected interpolation, B-spline, spatial, and rotation utilities used by parts of the framework.

\section{Evaluation Metrics}
\label{sec:setup_metrics}
\todoX{Define Computational Effort: Wall-clock CPU time, including notes on parallelization/multi-threading for MC-GBO and IPSO.}
\todoX{Define Solution Quality: The final objective cost J achieved (effort for spacecraft, effort + acceleration for the manipulator).}

The evaluation is organized into four metric groups. 
Reliability and computation time are reported for all attempts, whereas solution quality is evaluated only for successful solutions. 
Search-behavior metrics are reported for repeated runs and for the algorithms for which the corresponding internal statistics are available. 
The individual results sections specify the applicable metrics and reporting subsets for each experiment.

\paragraph{Reliability}
Reliability is characterized by the success rate and failure rate over all attempted runs. 
\ac{IPOPT} failures are classified as infeasible problem instances, maximum-iteration termination, timeouts, or other unexpected exceptions. 
A run is successful only when the solver returns converges with the resulting trajectory passing the applicable kinodynamic constraint checks.

\paragraph{Computation Time}
Computation time includes per test case statistics on wall-clock time, sequential-equivalent time for parallelized algorithms, time to first solution, and time to best solution. 
Solve-time distributions are summarized using the median, mean, standard deviation, and relevant quantiles. 
Quantile solve durations are reported where the number of trials supports a meaningful distributional comparison.

\paragraph{Solution Quality}
For successful solutions, the final objective cost is reported using the mean, standard deviation, median, and relevant quantiles, together with the best, worst, and interquartile-range costs when appropriate. 
Results also include the relative cost gap to the best solution found across all algorithms. 
The objective definition is problem-specific: spacecraft results use the control effort objective, while manipulator results include the specified control effort plus acceleration terms.

\paragraph{Search Behavior and Diversity}
Search behavior is analyzed to characterize local-minimum discovery and solution diversity. 
Metrics include the raw number of solutions, unique basin frequencies. 
Algorithm-specific statistics are reported when available: for \ac{P-HO}, final $\lambda=1$ solutions, tree size; for \ac{RRT*-GBO}, sampled nodes, accepted edges; and for \ac{IPSO}, particle evaluations, completed outer and inner iterations, and the number of solutions sent to \ac{GBO} refinement.

The complete metric inventory is defined here for consistency, but not every metric is relevant to every experiment. 
The results section therefore reports the metrics applicable to the algorithm and test case under study, while retaining the common definitions above for cross-algorithm comparisons.

\section{Problem 1: Spacecraft Attitude Slew}
\label{sec:setup_spacecraft}

\subsection{Physical Parameters}
The spacecraft inertia matrix denoted by $\mathbf{J}_{\mathrm{sc}}$ is set as a spherical inertia, $\mathbf{J}_{\mathrm{sc}} = 10000*\mathbf{I}$ kg·m².
The baseline control torque limits are set to $\boldsymbol{\tau}_{\max} = 200$ N·m, and the angular velocity limits are set to $\boldsymbol{\omega}_{\max} = 0.2$ rad/s (11.46 °/s).
If different torque or angular velocity limits are used for specific test cases, they are explicitly stated in the scenario description.
Both limits are defined in the spacecraft body frame.

\subsection{B-Spline Discretization}
For all test scenarios, the B-splines were parameterized via:
\begin{itemize}
    \item Fixed time horizon: $t_f = 60$ s
    \item B-spline degree: cubic $p = 3$
    \item Number of free control vertices: $n_{free} = 10$
    \item Number of boundary conditions: $n_{bc} = 6^\dagger$ equating to an initial and final angular orientation, zero angular velocity, and zero angular acceleration, $^\dagger$ except for two test cases that include additionally zero angular jerk $n_{bc} = 8$.
    \item Total number of control vertices: $n_{ctrl} = n_{free} + n_{bc}$
    \item Number of via points: $n_{via} = 61$
    \item Knot vector: $\operatorname{size}(\mathbf{t}) = n_{ctrl} + p + 1$
\end{itemize}

\subsection{Target (Ball) Parameters}

The ball's initial position, velocity, and trajectory start time are specified as follows:
\begin{align}
    {}^i\mathbf{p}_{b,0} &= [4.974756, -3.563887, 1.619703]^\top \text{ m}, \\
    {}^i\mathbf{v}_{b,0} &= [v_x, v_y, v_z]^\top \text{ m/s}, \\
    t_0 &= 0.058991 \text{ s}.
\end{align}
The velocity components $v_x$, $v_y$, and $v_z$ are the main parameters defining each ball catching test caseThe resulting trajectory of the ball is determined by the ballistic equation:
\begin{equation}
    {}^i\mathbf{p}_b(t_b) = {}^i\mathbf{p}_{b,0} + {}^i\mathbf{v}_{b,0} t_b + \frac{1}{2} {}^i\mathbf{g} t_b^2, 
    \quad t_b = t-t_0
\end{equation}

\subsection{B-Spline Discretization}

For all test scenarios, the clamped, uniform B-splines were parameterized via:
\begin{itemize}
    \item Fixed time horizon: $t_f = [0.06,1.8]$ s
    \item B-spline degree: cubic $p = 3$
    \item Number of free control vertices: $n_{free} = 6$
    \item Number of B-spline-embedded endpoint conditions: $n_{bc} = 5$. These are the initial joint position and the zero-velocity and zero-acceleration conditions at the initial and final boundaries that determine the corresponding endpoint control vertices. The terminal catching task is imposed separately through five scalar pose equalities (three position and two orientation); these constraints do not reduce the number of free B-spline control vertices, as described in \cref{sec:ocp}.
    \item Total number of control vertices: $n_{ctrl} = n_{free} + n_{bc}$
    \item Number of via points: $n_{via} = 20$
    \item Knot vector: $\operatorname{size}(\mathbf{t}) = n_{ctrl} + p + 1$
\end{itemize}

\subsection{Test Scenarios}
The ball-velocity test cases replicate the experiments of Lampariello et al.~\cite{Lampariello11}. 
The velocity combinations are taken from a lookup table containing 1,825 discrete 
velocity triplets and solutions. The table does not contain all possible combinations 
of the velocity component ranges; instead, it contains 22 distinct $v_x$ values, 
12 $v_y$ values, and 24 $v_z$ values combined into the 1,825 tested triplets.

Four algorithms are evaluated in the experiments: \ac{MC-GBO}, \ac{RRT*-GBO}, \ac{P-HO}, 
and a baseline comparison method: local optimization with a trivial initial guess. 
The trivial guess consists of setting all free control vertices to the root---
that is, setting every free control vertex to the initial joint
configuration $\mathbf{q}_0$. The initial guess for the final time is selected
as the time at which the ball passes closest, by measure of Euclidean distance, to the
end-effector position corresponding to $\mathbf{q}_0$.
This guess is naturally infeasible with respect to the \ac{NLPn} and is purely used
as the initial point for the local optimization.

Two evaluation sets are produced. The first evaluates the available
lookup-table cases broadly across the 1,825 recorded velocity triplets,
running a selection of 1000 random velocity sets. Each test case is allotted
a 30-minute optimization budget and ends when the first feasible solution is found
or the time budget is exhausted.
The second is a focused global-landscape study intended to explore each selected
case more thoroughly. For this study, 100 lookup-table rows are
selected evenly among the list of 1825 velocity triplets, 
so that the selected cases cover the range of velocity pairings throughout the
table rather than clustering in specific regions. Each selected velocity case is
assigned a two-hour optimization budget with no cap on the number of solutions.
The list of selected velocity cases for both evaluation sets is provided in \cref{app:selected_lut_rows}.
